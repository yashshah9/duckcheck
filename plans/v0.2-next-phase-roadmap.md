# v0.2 Next-Phase Roadmap — duckcheck

**Status:** v0.2.0 shipped (new check types, JUnit, env substitution; live Postgres container still open)  
**Target Version:** 0.2.0 – 0.6.0  
**Owner:** Yash Shah  
**Last Updated:** 2026-08-19  

---

## 1. Executive Summary

Evolve duckcheck from a **local file scanner** into a **production data quality CLI** for CI and orchestration: connect to Postgres/MySQL via DuckDB ATTACH, add freshness and volume checks, emit JUnit XML for CI dashboards, support custom SQL assertions, and ship Airflow/Dagster operators with PyPI distribution.

## 3. Milestone Breakdown

### Milestone M1 — Postgres/MySQL ATTACH (v0.2.0)

**Goal:** Run the same YAML check suite against live SQL databases without exporting to CSV.

#### Deliverables

- [x] Postgres/MySQL ATTACH stubs in the runner (`INSTALL/LOAD` + `ATTACH`)
- [x] Extended `SuiteSpec.source` — `postgres://` / `mysql://` URIs alongside file paths
- [x] `source_table` on the suite (table name only; dotted schemas not supported)
- [x] `${ENV}` substitution in source strings
- [x] `duckcheck run --source-table orders checks.yaml` override flag
- [ ] Integration test with Postgres container in `compose.yaml`
- [ ] Documentation: connection string examples, SSL options, read-only recommendation

#### YAML Schema Extension

```yaml
name: prod-orders
source: postgres://readonly:pass@localhost:5432/analytics
source_table: public.orders
checks:
  - name: order_id_unique
    type: unique
    table: orders
    column: order_id
```

#### Acceptance Criteria

| # | Criterion |
|---|-----------|
| AC1 | Run full check suite against Postgres test container in Docker CI |
| AC2 | MySQL ATTACH works with DuckDB MySQL extension loaded |
| AC3 | File-based sources (CSV/Parquet) remain backward compatible — no schema break |
| AC4 | Clear error when ATTACH fails (bad credentials, missing extension) |

#### Dependencies

- DuckDB Postgres scanner extension (bundled ≥1.0)
- DuckDB MySQL extension (may require explicit `INSTALL mysql; LOAD mysql;`)
- Testcontainers or compose service for Postgres in CI

#### Risks

| Risk | Mitigation |
|------|------------|
| DuckDB extension availability varies by platform | Document platform matrix; CI on linux/amd64 |
| Production DB load from full-table scans | Recommend read-only user; add `--sample N` future option |
| Connection string secrets in YAML | Support env var substitution `${DUCKCHECK_DB_URL}` |

**Estimate:** 1–2 weeks

### Milestone M2 — Freshness + Row Count Delta Checks (v0.2.0)

**Goal:** Detect stale pipelines and unexpected volume changes — the two most common production data quality failures.

#### Deliverables

- [x] `freshness` check type — `column` older than `max_age` (Ns/Nm/Nh/Nd)
- [x] `row_count` check type — `min_rows` / `max_rows` (baseline delta store still open)
- [ ] `duckcheck/state/` — SQLite or JSON baseline store for row counts
- [ ] `duckcheck baseline update checks.yaml` — persist current counts after known-good run
- [x] Check fields: `max_age`, `min_rows`, `max_rows`
- [ ] Unit tests with frozen clock for freshness edge cases

#### Check Type Reference

| Check Type | Required Fields | Pass Condition |
|------------|-----------------|--------------|
| `freshness` | `column`, `max_age` (e.g. `24h`, `7d`) | `MAX(column) >= now() - max_age` |
| `row_count_delta` | `tolerance_pct` or `min_rows`/`max_rows` | Row count within bounds vs baseline |

#### Example YAML

```yaml
checks:
  - name: orders_fresh
    type: freshness
    table: orders
    column: updated_at
    max_age: 24h
  - name: orders_volume
    type: row_count_delta
    table: orders
    tolerance_pct: 10
```

#### Acceptance Criteria

| # | Criterion |
|---|-----------|
| AC1 | Freshness check fails when max timestamp is older than `max_age` |
| AC2 | Row count delta fails when count deviates beyond `tolerance_pct` from baseline |
| AC3 | `baseline update` persists counts; subsequent run compares against them |
| AC4 | Human-readable failure messages include actual vs expected values |

#### Dependencies

- M1 ATTACH (freshness most valuable on live DBs; works on CSV with date columns too)
- SQLite stdlib for baseline store (no new dependency)

#### Risks

| Risk | Mitigation |
|------|------------|
| Timezone ambiguity on timestamp columns | Document UTC assumption; optional `timezone` field |
| Baseline drift after intentional backfill | `baseline update` command + `--ignore-baseline` escape hatch |

**Estimate:** 1–2 weeks

### Milestone M3 — JUnit XML CI Output (v0.3.0)

**Goal:** Integrate with GitHub Actions, GitLab CI, Jenkins, and other tools that consume JUnit reports.

#### Deliverables

- [x] `duckcheck run checks.yaml --junit results.xml`
- [x] `to_junit()` serializer (one `<testcase>` per check; `<failure>` on fail)
- [x] One `<testcase>` per check; `<failure>` with message on fail
- [x] Suite-level `<testsuite>` (timing attributes still open)
- [ ] `--format rich|json|junit` output format flag (default: rich)
- [ ] GitHub Actions workflow example in `examples/github-actions/`
- [ ] JSON output format for programmatic consumers

#### JUnit Mapping

| duckcheck | JUnit XML |
|-----------|-----------|
| Suite name | `<testsuite name="...">` |
| Check name | `<testcase name="...">` |
| FAIL | `<failure message="...">` |
| PASS | `<testcase>` with no failure |
| Exit code 1 | CI fails when any testcase fails |

#### Acceptance Criteria

| # | Criterion |
|---|-----------|
| AC1 | Generated XML validates against JUnit XSD |
| AC2 | GitHub Actions `publish-unit-test-result-action` parses output correctly |
| AC3 | Rich output unchanged when `--format` not specified (backward compatible) |
| AC4 | JSON format includes `passed`, `rows_failed`, `duration_ms` per check |

#### Dependencies

- None beyond v0.1 runner (can ship independently of M1/M2)

#### Risks

| Risk | Mitigation |
|------|------------|
| JUnit schema variants across CI tools | Target JUnit 10.x compatible subset; test against GH Actions |

**Estimate:** 1 week

### Milestone M4 — Custom SQL Checks (v0.3.0)

**Goal:** Escape hatch for assertions not covered by built-in check types — teams write DuckDB SQL returning a single scalar.

#### Deliverables

- [x] `custom_sql` check type — SELECT returning failing rows (0 rows = pass)
- [ ] `expect: 0` (default) — query must return 0 for pass
- [ ] `expect: "> 0"` / `"= 42"` comparison operators
- [x] SQL validation — reject non-SELECT statements
- [ ] Named parameter support via `${column}` substitution from check config
- [x] Example: `no_negative_amounts` in `examples/checks.yaml`

#### Example YAML

```yaml
checks:
  - name: no_orphan_line_items
    type: custom_sql
    query: |
      SELECT COUNT(*) FROM line_items li
      LEFT JOIN orders o ON li.order_id = o.id
      WHERE o.id IS NULL
    expect: 0
  - name: revenue_positive
    type: custom_sql
    query: SELECT COUNT(*) FROM orders WHERE total_amount < 0
    expect: 0
```

#### Acceptance Criteria

| # | Criterion |
|---|-----------|
| AC1 | Custom SQL check passes when query result matches `expect` |
| AC2 | Multi-statement SQL rejected at validation time |
| AC3 | Failure message includes query result and expected value |
| AC4 | Works against ATTACH sources and CSV sources identically |

#### Dependencies

- M1 ATTACH recommended for real-world custom SQL value

#### Risks

| Risk | Mitigation |
|------|------------|
| SQL injection via YAML | Parameterized substitution only; no string concat from untrusted input |
| Expensive queries in CI | Optional `--timeout 30s` per check |

**Estimate:** 1 week

### Milestone M5 — Airflow/Dagster Operator + PyPI Publish (v0.4.0 – v0.6.0)

**Goal:** Drop-in orchestration integration and public package distribution.

#### Deliverables

- [ ] PyPI publish pipeline in CI (tag-triggered `hatch publish`)
- [ ] `duckcheck-airflow` optional extra — `DuckCheckOperator` task
- [ ] `duckcheck-dagster` optional extra — `@duckcheck_op` decorator
- [ ] Operator inputs: `suite_path`, `conn_id` (Airflow), `format`, `fail_on_error`
- [ ] XCom / Dagster metadata output with check results summary
- [ ] `examples/airflow/dag_duckcheck.py` — sample DAG
- [ ] `examples/dagster/job_duckcheck.py` — sample job
- [ ] README badges: PyPI version, downloads

#### Operator Interface (Airflow)

```python
DuckCheckOperator(
    task_id="validate_orders",
    suite_path="checks/orders.yaml",
    conn_id="postgres_analytics",  # optional — overrides YAML source
    junit_output="/tmp/duckcheck-results.xml",
)
```

#### Acceptance Criteria

| # | Criterion |
|---|-----------|
| AC1 | `pip install duckcheck` from PyPI succeeds |
| AC2 | Airflow operator fails task on check failure; passes on success |
| AC3 | Dagster op emits structured metadata with pass/fail counts |
| AC4 | Operators installable as `pip install duckcheck[airflow]` without core bloat |

#### Dependencies

- M3 JUnit output (operators emit XML artifact)
- M1 ATTACH (operators typically target live DBs)
- PyPI account + trusted publishing token

#### Risks

| Risk | Mitigation |
|------|------------|
| Airflow/Dagster version matrix | Pin tested versions; document compatibility table |
| Optional dependency conflicts | Separate packages or extras; lazy imports |

**Estimate:** 2 weeks
